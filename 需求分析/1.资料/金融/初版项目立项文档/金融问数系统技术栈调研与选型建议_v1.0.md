# 金融问数系统技术栈调研与选型建议 v1.0

## 1. 结论

建议第一版采用“自研轻量业务系统 + 可替换 AI 能力”的路线，不直接基于某个大型开源问数平台二次开发。

推荐基线技术栈如下：

| 层级 | 推荐技术 | 定位 |
|---|---|---|
| 前端 | React + TypeScript + Vite + Ant Design + Apache ECharts | 问数对话、表格、趋势、排名、指标管理与审计页面 |
| 后端 API | Python 3.11/3.12 + FastAPI + Pydantic v2 | 业务 API、流式响应、权限校验与结果协议 |
| AI 流程编排 | LangGraph | 问题理解、澄清、语义检索、SQL 生成、校验、执行、解释与失败恢复 |
| 数据访问 | SQLAlchemy 2 + 对应数据库驱动 | 数据源连接、连接池与方言适配 |
| SQL 解析与防护 | SQLGlot + 数据库只读账号 + 表/字段白名单 + 超时/限行 | AST 检查、危险语句阻断、执行范围控制 |
| 应用与元数据存储 | PostgreSQL + Alembic | 用户、角色、指标、术语、样例、会话、审计和版本记录 |
| 语义检索 | PostgreSQL + pgvector；BGE-M3 作为首轮候选 | 第一版统一存储指标、字段、同义词、业务规则与历史正确样例 |
| 缓存与限流 | Redis | 会话临时状态、热点结果缓存、限流与分布式协调 |
| LLM 接入 | 统一 Provider Adapter，兼容 OpenAI-style API 与本地推理接口 | 避免绑定单一模型或厂商；具体模型通过金融 Text-to-SQL 测试集确定 |
| 观察与评测 | OpenTelemetry + Langfuse + 结构化日志 | 追踪问题解析、检索、模型调用、SQL、执行、结果和反馈 |
| 测试 | pytest + pytest-asyncio + Playwright + 金融黄金测试集 | 单元、集成、端到端与问数准确率回归 |
| 部署 | Docker Compose + Nginx | 第一版开发、演示和单机试运行；暂不引入集群编排 |
| 工程工具 | uv + Ruff + mypy；pnpm + ESLint | 依赖、格式、静态检查与可复现构建 |

其中，LLM 厂商与具体模型暂不锁定。这不是遗漏，而是必须由数据合规要求、预算、硬件条件和金融问数基准实测共同决定。其余栈可以作为 v1.1 文档的建议基线。

## 2. 调研范围与判断标准

本次对比 10 个核心或相邻项目/产品，覆盖：

- 开源自然语言问数与 Text-to-SQL 项目。
- 通用 AI 数据分析平台。
- 金融数据接入与金融 Agent 项目。
- BI 可视化与权限治理项目。
- 商业级语义问数产品的公开设计原则。

主要判断标准：

1. 与本项目“自然语言—业务语义—查询—结果解释”闭环的相似度。
2. 中文金融场景的适配空间。
3. 元数据、指标、同义词和业务口径管理能力。
4. SQL 执行安全、权限、审计和可追溯性。
5. 技术复杂度、维护成本和二次开发风险。
6. 上游维护状态与开源许可风险。
7. 是否适合作为第一版底座，而不只是功能演示。

### 3.2 关键观察

#### 观察一：语义层比“直接把全库结构交给模型”更重要

WrenAI 将模型、字段、关系和业务知识组织为 MDL；Snowflake 使用语义模型/语义视图；Databricks 要求配置指标、维度、过滤条件、同义词、样例 SQL 和可信资产。这三条路线共同指向一个结论：可靠问数必须先建立受治理的业务语义层。

因此，本项目第一版需要把以下内容作为正式数据资产，而不是只写在 Prompt 中：

- 业务对象和主题域。
- 表、字段及关系。
- 指标、维度、过滤条件和状态枚举。
- 同义词、缩写和业务别名。
- 已确认的业务规则。
- 已验证的自然语言问题、SQL 与预期结果。
- 版本、责任人、审核状态和生效时间。

#### 观察二：应评测“结果是否正确”，不能只评测“SQL 看起来像不像”

Snowflake 的 Verified Query Repository 把自然语言问题与已验证 SQL 关联，并在评测时避免把测试样例直接泄露给生成过程；Databricks 也把示例查询和人工修正作为持续提升手段。

本项目测试集应至少记录：

- 用户问题。
- 预期意图、指标、维度、时间与过滤条件。
- 参考 SQL。
- 预期结果或结果摘要。
- 权限上下文。
- 是否必须澄清。
- 允许误差。
- 失败类型。

核心评分应以执行结果正确率、口径命中率、权限合规率和澄清正确率为主，SQL 字符串相似度只作辅助。

#### 观察三：金融问数不能让模型直接获得无限制数据库权限

Superset 官方安全文档明确指出 BI 工具本身不能充当数据库防火墙，并建议使用专用、最小权限的只读数据库账号；PostgreSQL 提供行级安全策略。SQLGlot 可以解析 AST、识别语句类型和方言，但官方也明确说明“能解析”不等于“可安全执行”。

第一版至少需要以下防线：

1. 独立只读数据库账号。
2. 数据源、Schema、表和字段白名单。
3. 只允许单条只读查询。
4. AST 级危险操作与系统对象拦截。
5. 强制最大返回行数、执行超时和并发限制。
6. 执行前成本检查或计划检查。
7. 角色、机构与数据范围过滤。
8. 敏感字段脱敏。
9. 问题、语义解析、SQL、执行结果摘要、错误和用户反馈全链路审计。

#### 观察四：金融数据接入要区分“内部经营数据”和“公开市场数据”

OpenBB、FinRobot 与 [AKShare](https://github.com/akfamily/akshare) 适合公开市场、财报、宏观和投研数据，但本项目当前需求主体是客户、账户、交易、信贷、还款、逾期、风控和催收等内部经营数据。

因此：

- 第一版核心数据源应是 `finance-data` 对应的内部或演示数据库。
- OpenBB、AKShare 等只作为未来外部金融数据扩展候选。
- 不应在第一版为了“金融化”而引入行情、交易或量化框架。
- 外部数据源必须单独确认授权、稳定性、更新频率和商用条款。

## 4. 推荐总体架构

```text
用户与管理端
    ↓
React 问数界面 / 指标与元数据管理 / 审计页面
    ↓
FastAPI 业务接口与流式响应层
    ↓
身份认证、RBAC、机构数据范围、请求限流
    ↓
LangGraph 问数流程
    ├─ 问题要素识别
    ├─ 歧义与缺失条件检查
    ├─ 语义层检索
    ├─ SQL 生成
    ├─ SQL AST 与权限校验
    ├─ 只读查询执行
    ├─ 结果一致性检查
    └─ 表格/趋势/排名/解释生成
    ↓
数据与治理层
    ├─ PostgreSQL：用户、角色、指标、术语、样例、会话、审计
    ├─ pgvector：语义元数据与正确样例检索
    ├─ Redis：缓存、限流和短期状态
    └─ finance-data：只读业务数据源
    ↓
OpenTelemetry / Langfuse / 结构化日志 / 金融黄金测试集
```

## 5. 分层技术选型说明

### 5.1 前端

推荐：React + TypeScript + Vite + Ant Design + Apache ECharts。

原因：

- React/TypeScript 已在 WrenAI、Superset 等数据产品中得到验证，组件生态完整。
- Vite 足以支撑内部单页应用，第一版没有服务端渲染需求，不需要引入 Next.js 的全部复杂度。
- Ant Design 适合表单、表格、筛选、权限和管理后台。
- ECharts 适合趋势、分布、排名、金额和多维统计图表。

第一版不建议：同时引入多个 UI 组件库、低代码平台或微前端。

### 5.2 后端与接口

推荐：Python 3.11/3.12 + FastAPI + Pydantic v2 + SQLAlchemy 2 + Alembic。

原因：

- DB-GPT、Vanna、OpenBB 等项目均证明 Python/FastAPI 与 AI、数据访问和流式交互组合成熟。
- Pydantic 适合约束 LLM 结构化输出和业务 API 数据契约。
- SQLAlchemy 可统一连接池和多数据库方言接入，但具体方言仍需逐库测试。
- Alembic 用于应用元数据数据库的版本迁移，不触碰业务数据源结构。

### 5.3 问数工作流

推荐：LangGraph。

选择依据：LangGraph 官方支持状态持久化、人工介入、流式输出、故障恢复和执行续跑，适合将问数流程明确拆成可观察节点。相关能力见 [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) 与 [Human-in-the-loop](https://docs.langchain.com/oss/python/langchain/human-in-the-loop)。

建议节点：

1. `understand_question`
2. `resolve_context`
3. `check_ambiguity`
4. `retrieve_semantics`
5. `plan_query`
6. `generate_sql`
7. `validate_sql`
8. `authorize_query`
9. `execute_query`
10. `validate_result`
11. `compose_answer`
12. `record_feedback`

第一版不建议使用多 Agent 自主协作。这个问题本质上是受控状态流程，单图多节点更容易审计、测试和定位错误；只有后续出现明确的跨数据源复杂分析需求时，再评估多 Agent。

### 5.4 语义层与 RAG

推荐：YAML/JSON 语义定义 + Pydantic 校验 + PostgreSQL 版本记录 + pgvector 检索。

建议语义对象：

- `business_domain`
- `entity`
- `table`
- `column`
- `relationship`
- `metric`
- `dimension`
- `filter_rule`
- `enum_value`
- `synonym`
- `verified_query`
- `permission_scope`

第一版建议用 pgvector 而不是单独部署 Qdrant：语义数据量预计远小于业务明细数据，统一使用 PostgreSQL 能减少部署、备份、权限和运维成本。pgvector 支持精确检索及 HNSW/IVFFlat 索引，见 [pgvector 官方仓库](https://github.com/pgvector/pgvector)。

升级触发条件：如果语义向量达到较大规模、多租户隔离复杂、混合检索吞吐不足，或压测显示 PostgreSQL 检索影响主业务，再评估 Qdrant。

Embedding 首轮候选为 [BAAI BGE-M3](https://huggingface.co/BAAI/bge-m3)，因为其支持多语言、长文本以及稠密/稀疏/多向量检索。是否正式采用，仍需用项目中的中文金融术语、指标和问法做召回率测试。

### 5.5 SQL 生成、校验与执行

推荐：模型生成候选 SQL，SQLGlot 做 AST 解析与规则审查，数据库使用只读账号执行。

[SQLGlot](https://github.com/tobymao/sqlglot) 支持多种 SQL 方言、AST 遍历和转译，适合：

- 识别是否仅包含允许的查询语句。
- 提取访问的表、字段、函数和子查询。
- 应用白名单、黑名单和强制 `LIMIT`。
- 针对目标数据源输出指定方言。

但不能把 SQLGlot 当作唯一安全边界。数据库权限、RLS、超时、限行和审计必须同时存在。

### 5.6 LLM 与模型策略

推荐：在代码层定义统一 LLM Provider Adapter，不在第一版锁死单一厂商。

模型准入要求：

- 中文金融术语理解稳定。
- 支持结构化输出或工具调用。
- Text-to-SQL 复杂连接、聚合、时间条件和枚举映射表现合格。
- 能明确表达不确定性并触发澄清。
- 满足数据不留存、区域、日志和合规要求。
- 延迟和成本满足项目约束。

模型最终选择必须通过同一套金融黄金测试集比较，至少评测 2–3 个候选模型。未经合规确认，不向外部模型发送真实客户、账户、交易或风控明细。

### 5.7 权限与安全

推荐：OAuth2/OIDC + JWT + RBAC + 机构/数据域范围控制；PostgreSQL RLS 作为可用的数据层防线。

数据库策略参考 [PostgreSQL Row Security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)；最小权限原则参考 [Superset Security](https://github.com/apache/superset/blob/master/docs/admin_docs/security/security.mdx)。

第一版必须做到：

- AI 服务不保存明文数据源密码。
- LLM 不直接持有数据库凭据。
- 查询连接默认只读。
- 用户权限在生成 SQL 前后均检查。
- 返回结果再次执行敏感字段脱敏。
- 审计日志与业务数据分开授权。

### 5.8 可观测性与评测

推荐：OpenTelemetry + Langfuse + JSON 结构化日志。

[Langfuse](https://github.com/langfuse/langfuse) 支持 LLM、检索、工具调用、Prompt 版本、数据集和评测追踪，并可自托管；OpenTelemetry 用于统一常规服务追踪。

每次问数至少记录：

- `trace_id`
- 用户与角色摘要
- 原始问题与标准化问题
- 命中的指标、维度、术语和样例
- Prompt/语义层版本
- 模型与参数
- 生成 SQL 与校验结果
- 查询耗时、行数与错误类别
- 返回结果类型
- 用户反馈与人工修正

### 5.9 测试与验收

推荐：pytest + pytest-asyncio + Playwright + 金融黄金测试集。

必须区分：

- 单元测试：解析、口径、权限、SQL 规则和脱敏。
- 集成测试：语义检索、数据库连接和完整工作流。
- 端到端测试：问数页面、澄清、流式结果、图表和异常提示。
- AI 回归测试：同一测试集多次运行，统计结果正确率、口径命中率、澄清率、越权率和稳定性。

## 6. 不推荐的路线

### 6.1 直接 Fork Vanna 作为主项目

不推荐。其设计有参考价值，但仓库已归档，只读状态会带来安全修复和依赖升级风险。

### 6.2 直接在 DB-GPT 上做重度二开

暂不推荐。DB-GPT 功能完整，但本项目第一版业务边界明确，直接采用会引入沙箱、技能、多数据源、报表和通用 Agent 平台的大量复杂度。可用于原型对照或能力验证。

### 6.3 直接采用 WrenAI 全栈

暂不推荐。WrenAI 的语义层思想最值得借鉴，但其 Rust/DataFusion 语义核心更适合多数据源、平台型产品。第一版自建轻量语义层成本更可控。若后续目标变成企业级统一语义平台，再重新评估。

### 6.4 第一版就采用多 Agent

不推荐。自然语言问数需要确定性、权限和审计，多 Agent 会扩大状态、成本和错误归因难度。第一版以 LangGraph 单流程多节点为主。

### 6.5 第一版就引入 Kubernetes、独立向量数据库和消息队列

不推荐。当前没有高可用规模、并发量、向量规模和长任务吞吐证据。先使用 Docker Compose、PostgreSQL/pgvector 和 Redis；达到明确升级触发条件后再扩展。

## 7. 风险与待验证项

| 风险 | 影响 | 建议控制 |
|---|---|---|
| `finance-data` 的真实格式、表结构和数据量未知 | 数据库、驱动和检索设计可能变化 | 技术实施前先完成只读数据盘点 |
| 用户体系与机构权限规则未知 | 无法最终确定认证和 RLS 设计 | 由业务方提供角色、机构和数据范围矩阵 |
| LLM 部署边界未知 | 影响厂商、成本、硬件和合规 | 明确可否调用外部 API、数据是否可出域 |
| 指标口径未形成权威版本 | SQL 正确但业务结果可能错误 | 先建设指标卡和已验证查询库 |
| SQL 方言未知 | SQL 生成和校验策略可能变化 | 明确目标业务数据库，逐方言建立测试集 |
| 真实并发与响应时间目标未知 | Redis、异步任务和部署规模无法定量 | 给出目标并发、P95 和最大查询耗时 |
| 开源许可证 | 直接嵌入部分项目可能触发许可证义务 | 当前只借鉴架构；引入源码前单独审核许可 |

## 8. 需要用户审批的技术决策

请审批以下基线：

1. 是否同意采用“自研轻量业务系统”，不直接 Fork DB-GPT、WrenAI、Vanna。
2. 是否同意前端采用 React + TypeScript + Vite + Ant Design + ECharts。
3. 是否同意后端采用 Python 3.11/3.12 + FastAPI + Pydantic v2 + SQLAlchemy 2 + Alembic。
4. 是否同意问数工作流采用 LangGraph，第一版不采用多 Agent。
5. 是否同意 PostgreSQL 同时承载应用元数据、审计、工作流状态与 pgvector 语义检索。
6. 是否同意使用 SQLGlot + 只读数据库账号 + 白名单 + 超时/限行 + RLS 的多层查询防护。
7. 是否同意 Redis、OpenTelemetry、Langfuse、pytest、Playwright 和 Docker Compose 进入第一版基线。
8. 是否同意 LLM 厂商暂不锁定，先明确数据合规边界并用金融黄金测试集评测后决定。
9. 是否同意 BGE-M3 仅作为 Embedding 首轮候选，而非未经测试直接定版。
10. 请补充：目标业务数据库类型、是否允许外部模型 API、预计并发量、是否必须私有化部署。
